# Register-Pressure Optimization — Investigation and Plan

Investigation of whether `sarm`'s AArch64 assembly can be globally optimized
to reduce register pressure and register save/restore traffic.

Status: **investigation complete, implementation not started.** The only code
added so far is `scripts/regpressure.py`, a read-only analyzer that produced
every number below. No `.S` file has been modified.

---

## Summary — the premise needs adjusting

The brief targets "reducing register pressure, live ranges, and callee-saved
register traffic". Measured against the actual codebase, those three are not
equally available:

| Claim | Measured | Verdict |
|---|---|---|
| Pressure forces spills | Peak live GPRs: median **6**, max **25**, of 31 available. No function spills. | **No headroom.** One function (`x25519_fe_mul`) is even close. |
| Live ranges are too long | Long ranges exist, but they end at call sites, where a callee-saved register is *mandatory*. | **Mostly justified.** |
| Callee-saved traffic is wasteful | **589** save/restore instructions; ~**160** are recoverable in 35 functions. | **This is the real target.** |

So the optimization objective for this repo is narrower and more concrete than
"reduce register pressure":

> Eliminate callee-saved prologue/epilogue traffic in functions that preserve
> registers they do not need to preserve, without increasing stack usage or
> making the hot path slower.

Register pressure matters only as the *constraint* that says whether such a
change is possible — not as the thing being minimized.

### The blocking problem is measurement, not analysis

This is the finding that should drive sequencing. The brief says performance
must be the authority, and constrains against accepting a change without
measured improvement. Today that is impossible for essentially the whole repo:

- **1 of 165 functions has a benchmark** (`scripts/benchmarks/bench_memcpy.c`).
- **No `perf`** — macOS. Hardware counters are unavailable, so Phase 8 of the
  brief cannot be implemented as written.
- **No `llvm-mca`** (not in this toolchain, not via `xcrun`), so the existing
  harness's static throughput analysis is inert.
- The fallback benchmark — running a unit test binary 10× under wall clock —
  measures **0.02 s at 0.01 s resolution**, dominated by process startup. It
  cannot resolve a change to a function that runs in nanoseconds.

Building the register optimizer before fixing this would produce a system that
can only accept candidates on *static* metrics — precisely the failure mode the
brief prohibits ("a function using 10 registers with no spills may be
substantially better than one using 6 but requiring stack traffic"). **The
benchmark substrate must come first.** It also benefits the existing `speed`
strategy, which has the same gap.

## Deliverable 1 — Analysis of the existing assembly functions

165 analysable functions across 10 subsystems (269 `.global` symbols; the
remainder are data). Generated by `python3 scripts/regpressure.py`.

```
functions analysed                          : 165
peak GPR pressure (max / median)            : 25 / 6
functions with peak >= 24 (spill risk)      : 1
total save/restore instructions             : 589
functions preserving callee-saved GPRs      : 76
  ...holding a register never live across a call : 35
functions using the carry-flag return ABI   : 36
register-to-register movs                   : 837
```

Opportunity classification: **35 HIGH, 2 MEDIUM, 9 LOW, 108 NONE.**

### Where the recoverable traffic is

The cleanest wins are **true leaf functions** (no `bl`/`blr`/`svc`) that still
preserve callee-saved registers. A leaf function needs none: it may use all 18
caller-saved GPRs freely, so if peak pressure fits, the entire prologue,
epilogue and stack frame disappear.

| Function | Peak | Callee-saved held | S/R insns | Frame | Fits in caller-saved? |
|---|---|---|---|---|---|
| `h2_huffman_decode` | 14 | 10 (x19–x28) | 12 | 96 B | **YES** |
| `x25519_fe_mul` | 25 | 10 (x19–x28) | 10 | 96 B | PARTIAL (needs ~7) |
| `x25519_fe_scalar_product` | 12 | 2 | 2 | 32 B | **YES** |
| `x25519_fe_sqr_times` | 18 | 1 | 2 | 32 B | YES (exactly at limit) |

`h2_huffman_decode` is the flagship case and was verified by hand: zero calls,
zero syscalls, uses `x0–x3, x8–x10, x12, x13` plus all of `x19–x28`, peak
simultaneous pressure 14, and leaves **9 caller-saved registers untouched**
(`x4–x7, x11, x14–x17`). It can be reallocated entirely into caller-saved
registers, removing 10 save/restores, the `str x30`, and the whole 96-byte
frame — with no increase in stack or memory traffic. It sits on the HPACK
decode path, i.e. per-request hot code for HTTP/2.

The remaining 31 HIGH functions are non-leaf: they hold *some* callee-saved
registers whose values are never live across any of their call sites. Each such
register is one `stp`/`ldp` pair of pure overhead, recoverable only if a
caller-saved register is free at that point. Smaller wins, higher analysis cost.

The 9 LOW functions (`h2_hpack_decode_field`, `aes_gcm_encrypt/decrypt`,
`x25519`, `hmac_sha256`, …) carry 10–15 save/restores each that are **fully
justified** — every preserved register holds a value across a call. These should
be left alone; they are the "already optimal" set the brief says not to spend
effort on.

## Deliverable 2 — Analysis of the existing Python optimizer

`scripts/` already contains a well-structured harness implementing
`docs/OPTIMISATION.MD`: `optimizer.py` (the loop), `abi.py` (static ABI gate),
`benchmark.py`, `compiler.py`, `disassembler.py`, `perf.py`, `mca.py`,
`differential.py`, `llm.py`, `mutations/`, and the `arm-optimize.py` CLI.

**It generalizes cleanly.** The pipeline in `optimizer.py:331-487` is already
the shape the brief asks for: propose → ABI-check → install → test →
differential → benchmark → keep/reject, with full artifact archiving. A second
optimization framework should *not* be built.

Three changes are needed to support strategies:

1. **The accept/reject rule is hardwired to runtime.** `optimizer.py:444` is a
   bare `runtime < best * (1 - min_improvement/100)`. There is no scoring
   abstraction. This is the single seam where a `Strategy`/fitness object must
   be introduced.
2. **A benchmark is mandatory** (`optimizer.py:298-302` raises without one), yet
   only `memcpy` has one. This is what limits the harness to a single function
   today.
3. **The mutations are memcpy-specific** — `unroll the 16-byte ldp/stp loop`,
   `32-byte NEON ld1/st1 main loop`. Only `remove_redundant_mov` and
   `reschedule` are general. A register strategy needs its own mutation family.

### Defects found in the existing tooling

Both must be fixed before any transformation is trusted, because both silently
produce *wrong* analysis rather than failing:

- **`abi.py:129` discards every line starting with `.` before matching labels.**
  All **393** `.L…` local labels in `src/` are therefore invisible; branch
  targets never resolve, back edges vanish, and no loop is ever detected. The
  ABI checker's core claim — "this register is restored on *every* path to
  `ret`" — rests on a control-flow graph that, for most functions here, has no
  edges. The static safety gate is substantially weaker than it appears.
  I hit this directly: the analyzer's first run reported `raw_read_exact`'s x19
  as removable when it is plainly live across the syscall in the loop.
  `scripts/regpressure.py` carries its own corrected parser; `abi.py` should be
  fixed too, and that fix is independently valuable.
- **Macros are never expanded.** `src/defs.S` defines 13 macros used ~500 times
  across 82 files. `ldr_l`/`str_l` write a hidden scratch register (`x9` by
  default) and `SCWISVC` expands to `svc`. Unexpanded, liveness misses those
  writes and every syscall site looks like straight-line code — which is exactly
  what made four syscall-using functions initially look like leaves.

## Deliverable 3 — Proposed architecture

Extend the existing engine rather than forking it.

```
arm-optimize.py --strategy {speed|registers|combined}
        │
        ▼
  Strategy  ── candidates() ── score() ── accept()
        │            │            │
        │            │            └── fitness + hard constraints
        │            └── mutations/registers.py  (+ optional LLM)
        │
        └── unchanged: install → ABI check → build → tests
                       → differential → benchmark → archive
```

Concretely:

- `scripts/strategy.py` — a `Strategy` protocol: `propose(function_text) ->
  [Candidate]`, `measure(...) -> Metrics`, `score(Metrics) -> float`,
  `accept(before, after) -> (bool, reason)`.
- `scripts/regpressure.py` *(exists)* — analyzer + report. Read-only.
- `scripts/mutations/registers.py` — the register transformation family.
- `optimizer.py` — replace the hardwired comparison at line 444 with
  `strategy.accept(...)`; make `benchmark_cmd` optional only when the strategy
  declares it does not need one (it always will for acceptance; see below).

## Deliverable 4 — Highest-value functions, in order

1. **`h2_huffman_decode`** — leaf, 10 callee-saved removable, 96 B frame
   removable, hot path. Highest value and lowest risk; the whole thing is
   verifiable statically.
2. **`x25519_fe_scalar_product`**, **`x25519_fe_sqr_times`** — leaf, small,
   1–2 registers each. Good second cases: cheap to prove, exercise the machinery.
3. **`x25519_fe_mul`** — the only genuine *pressure* case (peak 25). Partial
   win; needs real allocation, not reassignment.
4. **`ghash`** (6 unjustified), **`reply_status`** (4), **`tls_server_handshake`**
   (4), **`h2_process_request`** (3), **`parse_range`** (3) — non-leaf, moderate.
5. Everything else — defer. The 108 NONE functions should not be touched.

Deliberately excluded: the 9 LOW functions, whose save/restore traffic is fully
justified.

## Deliverable 5 — Candidate transformations

Ordered by safety. Each changes one function and one conceptual thing.

1. **Leaf callee-saved elimination.** In a function with no `bl`/`blr`/`svc`,
   rewrite `x19…x28` to unused caller-saved registers and delete the prologue,
   epilogue and frame. Requires: peak pressure ≤ available caller-saved count.
   Purely mechanical, and the strongest win.
2. **Unjustified callee-saved demotion.** In a non-leaf function, move a value
   never live across any call from a callee-saved to a free caller-saved
   register; drop its save/restore pair. Requires interference checking against
   the call-clobber set.
3. **Frame-size reduction.** After 1 or 2, shrink `sub sp, sp, #N` to the
   still-needed size, preserving 16-byte alignment. Never increases stack.
4. **ABI-shuffle mov elimination.** 105 of the 837 reg-to-reg movs are
   `arg ← arg` shuffles. Some vanish under renaming. (The other 69% are
   `callee ↔ arg` around calls and are inherent, not waste.)
5. **Live-range shortening / rescheduling.** Sink a definition toward its use to
   free a register earlier. **Highest risk** — see the flag hazard below.

### Constraint the brief does not mention: NZCV is part of the ABI

**36 functions return status in the carry flag** ("carry clear = success / carry
set = failure"), spanning 55 source files. The condition flags are therefore
live-out values, and `abi.py` does not model them at all.

This makes transformation 5 dangerous: any reordering that moves a
flag-setting instruction (`adds`, `subs`, `cmp`, `ccmp`, or a careless `add`→
`adds`) between the flag-setting site and the `ret` silently corrupts the return
value of a function whose data results still look correct. Unit tests that only
check returned *data* will not catch it. **NZCV must be modelled as a live
value before any reordering transformation is enabled.** Transformations 1–4 do
not move flag-setting instructions and are safe under renaming alone.

Two further hazards: `strlen` uses a **non-standard ABI** (argument in x1, not
x0), and the "Clobbered Registers" header comments — present on 207 functions —
are hand-maintained documentation that any transformation must update, or they
become actively misleading.

## Deliverable 6 — Testing strategy

Four gates, cheapest first:

1. **Analyzer self-validation.** The 207 documented "Clobbered Registers"
   headers are a ground-truth oracle: the analyzer's computed clobber set must
   be a subset. Any disagreement is a bug in the analyzer *or* a stale comment —
   both worth knowing. Run this before trusting any transformation.
2. **Static ABI gate** — existing `abi.py`, once the label bug is fixed, plus
   NZCV liveness.
3. **Unit tests** — `make -C tests/unit test`. Coverage is good: dedicated
   binaries exist for the crypto and h2/hpack functions that matter here.
4. **Differential + integration** — `scripts/differential.py`, then
   `tests/test_files.sh`, `test_security.sh`, `test_protocols.sh`, and
   `tests/h2_browser_sim.py` for end-to-end protocol behaviour.

For a register *renaming* transformation there is a fifth, decisive gate:
**the disassembly of the function body should differ only in register numbers
and the removed prologue/epilogue.** A structural diff of the objdump output
catches an entire class of mistakes without executing anything.

## Deliverable 7 — Benchmarking strategy

This is the prerequisite, not an afterthought.

1. **Per-function microbenchmarks** on the `bench_memcpy.c` pattern — a C driver
   linking the function's own `.S`, emitting `{"runtime_ns": …}`, using
   best-of-N over inner loops of ≥10⁵ iterations. Needed at minimum for
   `h2_huffman_decode`, the two small x25519 helpers, `x25519_fe_mul`, and
   `ghash`. The existing `scripts/benchmarks/Makefile` extends naturally.
2. **Remove the wall-clock fallback** in `arm-optimize.py:136-141`, or make it
   refuse to gate acceptance. It cannot resolve the effects being measured, and
   silently accepting on it is worse than having no benchmark.
3. **No hardware counters.** With `perf` and `llvm-mca` both unavailable,
   substitute: static instruction counts and `objdump` diffs (reliable, exact)
   for the instruction-level story, and `xctrace` (present at `/usr/bin/xctrace`)
   if sampled counters are wanted later. Do not pretend to have counter data.
4. **Noise discipline.** Median of ≥5 rounds; reject any improvement inside
   measurement noise. Target: Apple M3 Pro (`--target apple-silicon`). Results
   are not portable to Cortex/Neoverse — record the target with every result.

## Deliverable 8 — Scoring / fitness function

Hard constraints first — any violation rejects outright, regardless of speed:

```
correctness / differential failure  -> reject
ABI or NZCV-liveness violation      -> reject
stack usage increased               -> reject
heap usage or dynamic allocation    -> reject
loads/stores increased              -> reject
runtime regression beyond noise     -> reject
```

Then, among survivors:

```
score =  w1 * runtime_ns            (primary, measured)
       + w2 * save_restore_insns
       + w3 * instruction_count
       + w4 * load_store_count
       + w5 * peak_pressure         (tie-breaker only)
       + w6 * stack_bytes
```

Two deliberate choices. **Peak pressure is a tie-breaker, not a goal** — it is
the constraint that permits a transformation, and rewarding it directly would
recreate the "optimize for register count" failure the brief warns against.
And **an accepted change needs either a measured speedup or a strictly smaller
instruction/save-restore count with no measurable regression** — which is what
makes `h2_huffman_decode` acceptable even if the benchmark cannot resolve 10
removed instructions. Weights to be fitted on the first accepted candidates, not
assumed.

## Deliverable 9 — Optional local-LLM candidate generation

Ollama is installed. But this is the **lowest-value component here** and should
be built last, if at all.

The high-value transformations (1–4 above) are mechanical: given correct
liveness, a deterministic pass finds and applies them exactly, and the search
space is small enough to enumerate. An LLM adds nondeterminism and validation
cost for candidates a solver produces exactly. Its plausible niche is
transformation 5 (rescheduling) and `x25519_fe_mul`'s genuine allocation
problem, where the space is large and heuristics run out.

If built: keep the existing role split (`llm.py` generator + judge), feed it the
`regpressure.py` analysis as context, constrain it to one small isolated change,
and keep every existing gate. The LLM never decides correctness — the existing
architecture already gets this right.

## Deliverable 10 — Implementation steps

Each step is independently testable and independently valuable. Steps 1–3 are
worth doing even if the optimizer is never built.

| # | Step | Gate |
|---|---|---|
| 1 | Fix the label bug in `abi.py:129`; add macro expansion | ABI checker detects loops; existing tests still pass |
| 2 | Validate `regpressure.py` against the 207 documented clobber headers | Computed ⊆ documented, or discrepancy explained |
| 3 | Add NZCV liveness to `abi.py` | Flags reported live-out for the 36 carry-ABI functions |
| 4 | Write `bench_h2_huffman_decode.c` | Stable ns-resolution measurement, <2% round variance |
| 5 | Hand-apply transformation 1 to `h2_huffman_decode`; measure | All gates pass; −10 S/R, −96 B stack, no regression |
| 6 | Introduce `Strategy` at `optimizer.py:444`; port `speed` to it | `--strategy speed` reproduces today's behaviour exactly |
| 7 | Add `mutations/registers.py` implementing transformation 1 | Reproduces step 5's result automatically |
| 8 | Add `--strategy registers` + transformations 2–4 | Wins on the ranked list, each individually benchmarked |
| 9 | Extend benchmarks to the rest of the top-10 | — |
| 10 | `--strategy combined`; optional LLM for step 5 / `x25519_fe_mul` | — |

**Step 5 is the decision point.** It is a single hand-applied change to one
function, fully verifiable, and it answers the real question — is the saved
prologue/epilogue measurable at all? If it is not, steps 6–10 should be scoped
down to the report plus a handful of hand-applied changes, rather than a search
system whose acceptance criterion cannot be evaluated.

## Answering the brief's final question

> For every assembly function in sarm, can we change register allocation,
> lifetimes, ordering or temporaries so it runs faster or needs fewer register
> save/restore operations, without increasing stack/heap usage or breaking
> correctness?

For **35 of 165 functions**, yes — by removing callee-saved registers that hold
no value across any call, worth roughly **160 of the 589 save/restore
instructions** plus associated stack frames. One function
(`h2_huffman_decode`) can shed its entire prologue, epilogue and 96-byte frame.

For the other **130**, no: their register usage is already tight, or their
callee-saved traffic is genuinely required across calls.

There is **no spill problem to solve** — the codebase does not spill. Speed
gains will come from removing fixed prologue/epilogue overhead in hot,
frequently-called functions, not from relieving pressure. Whether that overhead
is measurable is an open empirical question that step 5 answers cheaply, and it
should be answered before the full system is built.
