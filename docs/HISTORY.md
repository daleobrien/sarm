# History — what changed, what it measured, what it taught

A record of how `sarm` got from "HTTP/1 server in assembly" to "TLS 1.3 +
HTTP/2 server in assembly, ~5x faster per connection than when it first worked".
Kept because the *method* is more reusable than any individual patch: every
entry below says what was measured, what was proved, and what the result
implied about where to look next.

Full rationale for any entry is in its commit message (`git log`). The task
briefs that drove the optimisation work are in `prompts/`.

---

## The rules that came out of it

These were learned the expensive way. They are the reason the numbers below
are believable.

1. **Profile before choosing a target; re-profile after every win.** Every
   optimisation here changed the ranking. Twice the "obvious" next target
   (per-byte AES-GCM, register pressure) was measurably not worth doing.
2. **A static ranking is not evidence.** Instruction counts, register counts
   and "this looks expensive" all disagreed with the sampler at some point.
   This is now enforced in code: a non-speed strategy in `scripts/strategy.py`
   refuses to construct unless its target is a measured line item in the
   profile table below.
3. **Derive and prove in Python first, then port.** Every piece of P-256 and
   GHASH arithmetic here was generated by a script in `scripts/` that models
   the *exact* word-and-carry sequence the assembly executes — not the
   mathematical identity. A model that only computes the right answer cannot
   catch a carry bug; a model that executes the same steps can.
4. **A reference implementation is evidence only where it is faithful.** The
   P-256 field-multiply work found a bug in `p256_reduce`'s Python reference
   that had been load-bearing for two previous changes. The assembly was right.
   Random testing had missed it for 200,000 cases because the failing shape is
   essentially unreachable at random.
5. **Cross-check against something that shares no code.** Inversions are
   re-checked with `a * a⁻¹ == 1` through the *Barrett* multiply; the comb is
   checked against the untouched double-and-add on every `make test`; signatures
   are checked against OpenSSL.
6. **Measure baseline and candidate in the same session, alternating.** A
   freshly launched process reads ~8.4 µs against a steady-state ~5.3 µs on
   this machine from frequency ramp alone. Numbers from different days do not
   compare.
7. **Keep controls in every benchmark table.** A row that should *not* move,
   and doesn't, is what distinguishes a real win from a machine in a good mood.
8. **State the noise floor and respect it.** Several genuinely-faster-looking
   changes were rejected because their ceiling sat below the measured noise.
9. **Verify syscall numbers and ABI details on the machine**, with a probe —
   don't recall them.

All measurements: Apple M3 Pro, macOS 27.0, arm64, loopback. They do not
transfer to Cortex/Neoverse.

## Correctness work

### Three HTTP/2 bugs a browser found and `curl` couldn't

Diagnosed from a WebKit HAR where a 77 KB JS asset never completed while
smaller assets did. `curl` and `nghttp` both hid the bugs — they grant
multi-megabyte flow-control windows up front and don't reuse a connection hard
enough to wrap the stream table. Fixed by writing a frame-level browser
simulator (`tests/h2_browser_sim.py`, dependency-free stdlib):

1. `SETTINGS_INITIAL_WINDOW_SIZE` was never applied to already-open streams.
2. A `WINDOW_UPDATE` for a recently-closed stream killed the whole connection.
3. The server served one connection at a time and never forked.

   *No longer true.* `2dbbd23` ("Better forking", 2026-08-16) reinstated a
   `fork()` per accepted connection, precisely because serving a persistent
   HTTP/2 connection on the accept loop stranded every other connection in the
   listen backlog. This entry — and several others in the docs — was written
   afterwards from the pre-fork mental model; see `docs/ARCHITECTURE.md`.

Also fixed: settings stored with `str w7` into 8-byte fields left a stale
`0xFFFFFFFF` in the upper half of `H2C_SETTINGS_MAX_HEADER_LIST_SIZE`.

**Learning:** the test client's generosity is part of the test. Scenarios that
mimic real browser frame patterns found what conformance tools could not.

### Making the analysis tooling sound (`prompts/01`)

The static gate every optimiser candidate passes through was unsound three ways,
each producing confidently wrong answers:

- **Local labels were invisible.** `abi.py` dropped every line starting with `.`
  before testing for a label, discarding all 393 `.L` labels — so branch targets
  didn't resolve, back edges vanished, and "callee-saved registers are restored
  on every path" rested on a CFG with almost no edges. `regpressure.py` carried a
  *corrected copy* of the parser, and that divergence is exactly how the bug
  survived. Both now share `scripts/asmparse.py`. Detected loops: 0 → 81 of 173.
- **Macros were never expanded.** `ldr_l`/`str_l` write a hidden scratch
  register and `SCWISVC` expands to `svc`, so syscall sites looked like
  straight-line leaf code and their callee-saved registers looked removable.
- **NZCV was not modelled.** 55 regions return status in the carry flag, making
  the condition flags a live-out ABI value. Now tracked as a value, differentially
  against the function being replaced.

The unit of analysis became a *region*, not a `.global` symbol — `.Lgcm_ghash_run`
is the real GHASH implementation and the exported `ghash` symbol has zero call
sites. `validate_clobbers.py` then checked the analyzer against 207 hand-written
`// Clobbered Registers:` headers, which found two more soundness bugs and two
genuine ABI violations in `src/`.

**Learning:** two parsers of the same thing will diverge, and the divergence will
hide a bug. Also: hand-written doc headers are a free, strong correctness oracle.

## Performance work

### GHASH — 4 blocks per reduction (`prompts/03`)

The Horner loop processed one block at a time, leaving PMULL/PMULL2 pipelining
mostly unused. Precompute `H²..H⁴` once per call (only when ≥4 blocks remain, so
small AAD calls are unaffected) and process 4 blocks per iteration: three of the
four terms depend only on freshly loaded data rather than the previous
accumulator, and all four unreduced Karatsuba products are summed and reduced
once. The ring-level regrouping and the reduce-once identity were proved in
Python before any assembly was written.

**GHASH ~3x (7.13 → 2.3–2.4 ns/block); `aes_gcm_encrypt` ~1.9x (2113 → ~1075 ns).**

### P-256 reduction — Barrett → Solinas folding (`prompts/04`)

`p256_reduce` was ~73% of `p256_fe_mul`. P-256's modulus is a Solinas prime, so
a multiplication-free fold applies. The fold table was derived from first
principles by repeatedly applying `2²⁵⁶ ≡ 2²²⁴ − 2¹⁹² − 2⁹⁶ + 1 (mod p)`, not
transcribed from a reference — then verified with a Python oracle (2M+ cases), a
hardware-faithful simulation of the exact ASR/AND carry semantics (2M+ cases), a
differential run against the compiled assembly (3M cases) and a 292-vector
permanent regression suite, all *before* the Barrett implementation was touched.
The carry bound the correction rounds are sized against was proved exactly by
linear-extrema search, not sampled.

**`p256_reduce` 5.1x, `p256_fe_mul` 2.9x, `p256_point_mul` 2.7x, ECDSA sign 2.6x,
handshake CPU roughly halved.** No multiplies, no calls, no stack (was 192 bytes),
still branchless.

### P-256 `k*G` — fixed-base comb (`prompts/04`, gated on a re-profile)

The generic ladder walks 256 bits doing a double *and* a general addition per
bit — and the general addition internally computes a whole doubling plus twelve
`cmov`s to cover cases a fixed-base comb structurally cannot hit. That's ~9,200
field multiplies per scalar multiplication. Decomposing `k` over its 64
little-endian nibbles into a precomputed table makes it 64 mixed additions and
zero doublings: **~700 field multiplies plus one shared inversion.**

The cheap `p256_point_add_affine` has no doubling fallback and no infinity
handling — that is the entire source of its speed — so the two preconditions
were *proved* against the curve order rather than assumed
(`scripts/p256_comb_derivation.py`): the accumulator can never equal ±the table
point, because the largest addend anywhere is `15·2²⁵² < n`, and the negation
case requires `k == n` exactly, for which the true product is infinity and the
comb returns `(0,0)` bit-identically to the generic path.

| | before | after | |
|---|---:|---:|---:|
| `k*G` | 320.2 µs | **38.5 µs** | 8.32x |
| `p256_ecdsa_sign_with_k` | 354.7 µs | **87.9 µs** | 4.03x |
| handshake connection | 531.2 µs | **260.7 µs** | 2.04x |
| request on an established connection | 12.03 µs | 12.04 µs | unchanged (control) |
| stripped binary | 229,176 B | 295,400 B | **+66,224 B** |

The binary cost is essentially all table; a 3-bit comb (38.5 KB, 86 additions) is
the dial if it ever needs to shrink. `p256_point_mul` is untouched and still
serves variable-base work.

### P-256 `k⁻¹ mod n` — Montgomery multiply + addition chain

Once the comb removed `k*G` from first place, `p256_scalar_inv` was 45.2 µs of an
86.4 µs signature. It was paying twice over, and both factors changed:

- **The multiply.** Barrett reduction here is two further `bn_mul` calls (5×5 and
  5×4) — 45 limb products to reduce a result that took 16 to compute. Montgomery
  needs 20, and as a dedicated 4-limb routine it sheds three calls and a generic
  index-driven loop. **107 → 11.7 ns.**
- **The schedule.** `n−2` is a public constant, so the operation order is free.
  Its binary form has structure — a 32-bit run of ones, 32 zeros, a 65-bit run,
  then 128 bits whose runs are all ≤6 — and a ladder of `x^(2^k − 1)` values
  covers it in 257 squarings + 43 multiplies = **300 modular multiplications vs
  square-and-multiply's 425**. It ships as a 44-instruction, 180-byte program
  that `inv.S` interprets, rather than ~5 KB of unrolled calls.

**`p256_scalar_inv` 45.2 → 5.3 µs (8.53x); signing 86.4 → 45.8 µs (1.89x).**

The two factors don't compose to 12.9x, and the benchmark says so out loud — it
prints `mults_per_inv` ≈ 470 rather than 300, because the chain is *latency*-bound
(each squaring consumes the previous result) while the 11.7 ns microbenchmark is a
pipelined throughput figure. 17.7 ns per step is the honest number on this workload.

**Learning:** publish the number that contradicts your headline. A benchmark that
can only agree with you isn't measuring.

### P-256 field product — unrolled 4×4

`p256_fe_mul` reached `p256_bn_mul`, a generic `(na × nb)` schoolbook loop, for a
shape that is always 4×4 — paying a load, a store, two index computations and two
branches per limb product, and rebuilding the carry from two `cset`s each time
because NZCV can't survive the back-edge. Unrolled, the accumulator is eight
registers and the carry stays in NZCV across a whole row. The 512-bit product also
stopped touching memory: it lands directly in the eight registers `p256_reduce`
reads, and control *falls into* that function past its four `ldp`s — removing the
stack buffer, eight stores, eight loads and two call/return pairs. With nothing
called and nothing spilled, `p256_fe_mul` is a leaf: no frame, no callee-saved
register, no `x30`. The whole product had to fit in `x0`–`x17`, and it fits
exactly at eighteen registers.

The shape rests on one bound — row `i` cannot carry out of `T[i+4]` — which is
forced rather than observed, and `scripts/p256_fe_mul_derivation.py` proves it at
its extremes then replays the transcribed instruction sequence with it as an
assertion.

| | before | after | |
|---|---:|---:|---:|
| `p256_fe_mul` | 33.9 ns | **17.2 ns** | 1.97x |
| the 4×4 product alone | ~26.7 ns | **~6.1 ns** | ~4.4x |
| `p256_point_mul_base` | 39.4 µs | **26.4 µs** | 1.49x |
| `p256_ecdsa_sign_with_k` | 45.7 µs | **31.6 µs** | 1.45x |
| `p256_reduce`, `p256_scalar_inv`, `p256_scalar_mont_mul` | — | — | unchanged (controls) |

This is the change that found the reference-implementation bug described in rule 4.

### Entropy — `/dev/urandom` → `getentropy(2)`

`crypto_random_bytes` opened, read and closed `/dev/urandom` on every call. The
telling number wasn't the total but its *flatness*: 8.88 µs at 16 bytes, 8.93 at
64 — four times the data for 0.5% more cost, so essentially none of it was moving
bytes. It was path resolution. `getentropy(2)` (`getrandom(2)` on Linux) is one
syscall to the same kernel CSPRNG with no descriptor in between. Three calls per
connection (server random, ephemeral X25519 key, ECDSA nonce) made this ~27 µs of
a ~235 µs connection.

**8.88 → 0.79 µs, 11.2x; 11.80% → 0.42% of handshake busy samples; handshake
connection 235.2 → 192.4 µs.**

The syscall number and its 256-byte cap were confirmed with a direct `svc` probe
on the machine rather than recalled — which is why the assembly loops over chunks.
That loop was mutation-tested: breaking the pointer advance between chunks fails
3 assertions, which matters because a skipped chunk leaves 256 bytes of a key
buffer predictable while every 32-byte test still passes.

## Changes deliberately *not* made

These are as valuable as the wins — each one is an afternoon nobody needs to
spend again.

- **Register-pressure optimisation** (`prompts/05`, `prompts/07`). Peak live GPRs:
  median 6, max 25, of 31. Nothing spills. Of 589 save/restore instructions ~160
  looked recoverable, but every candidate the fresh profile surfaced either has no
  frame to remove, runs too few times per connection to matter, or has its one
  "unjustified" register paired in the same `stp`/`ldp` as a justified one — so
  removing it saves zero static instructions without restructuring the function.
  Analytical ceiling for the strongest candidate: **~0.36% of a connection**, an
  order of magnitude below the noise floor.
- **Response-path precomputation** (`prompts/08`). Lookup, header construction,
  HPACK and frame construction are one function (`h2_write_headers.S`) and
  together measure **≤0.15 µs, ≤0.02% of a connection**. The one real signal, the
  body `memcpy`, is ~1.70 µs for a 76,739 B transfer — 0.26% of a page-load
  connection *at 100% elimination*, below the stated noise floors. No `.S` file
  changed.
- **A hash table for the embedded lookup** (`prompts/10`). Three half-built pieces
  of an FNV-1a lookup existed and none was wired up. The cleaned-up linear scan
  measures **~7 ns/call** against the real 6-entry table (worst case ~9 ns), which
  is ~0.001% of a connection and matches the profiler's independent finding of
  **0 self-time samples across 56,935**. The unused mechanism was deleted rather
  than finished, and `lookup_embedded` got its first direct unit tests.

**Learning:** "delete the half-built thing" is a legitimate outcome of an
optimisation task, and shipping the measurement that says so is what stops it
being re-proposed.

i.e. **after** the GHASH and Solinas work, **before** the comb, the scalar

Sustained throughput on warm connections (`scripts/benchmarks/rps_bench.sh`,
4 threads, 20 connections, 5 s, `GET /`):

| Protocol | Req/s |
|---|---:|
| HTTP/1.1 | 16,806 |
| HTTP/2 (h2c) | 247,442 |
| HTTP/2 + TLS 1.3 | 238,298 |

TLS costs ~4% *per request* at steady state — the handshake is a separate
per-connection fixed cost, which is what all the P-256 work above was aimed at.
HTTP/1.1's figure includes socket read errors under concurrent keep-alive load
(~10k over ~90k requests) that don't appear on the HTTP/2 paths; `wrk` nets them
out of the number.

**Explained since.** sarm has no HTTP/1 keep-alive: every response carries
`Connection: close` and the server closes immediately, while `wrk` runs in
keep-alive mode and intends to reuse the connection. The errors are `wrk`
observing closes it did not expect. They are a subset rather than one per
request (~10k of ~90k), which fits a timing race — the close landing after
`wrk` has already written the next request — rather than every close being
counted. The HTTP/2 paths are unaffected because those connections are
genuinely persistent.

This is also why the HTTP/1.1 figure sits an order of magnitude below h2c on
the same server and asset: without keep-alive, every request costs a fresh
connection and a fresh `fork()`. See `docs/MULTICORE-BASELINE.md` and `Plan.md`
Phase 1.

## Open items

- **Re-profile.** The table above predates the last four optimisations.
- **X25519 is now the largest crypto cost in a handshake** — 13.3% of busy samples
  against 8.0% for all of P-256 — and has had none of the attention P-256 has had.
- **Roughly half a connection is kernel time** in `read`/`write`. The field-product
  change moved user CPU 120.8 → 111.7 µs while leaving total CPU inside the noise,
  which is what said the syscall path had become the thing setting connection cost.
- `h2_write_body.S`'s flow-control wait loop reads frames into `buf`, the
  connection loop's own buffer, clobbering unconsumed bytes. Latent over TLS
  (leftovers live in the TLS stage buffer), live for cleartext h2c.
- `aes128_encrypt` writes callee-saved `v8`–`v11` without restoring them, and
  `h2_verify_preface` writes `x21` while saving only `x29`/`x30`/`x19`/`x20`.
  Both reported by the ABI checker, both still open.
- Constant-time claims throughout are **structural arguments about emitted
  instructions** — no dudect-style timing test exists in this repo and there is no
  PMU access on this machine.
- `PLAN.MD` phases 23–26 (TLS negative tests, HTTP/2-over-TLS negative tests,
  security hardening, remaining optimisation) are not complete.
- `tests/h2_browser_sim.py` is not wired into `make test`; it needs start/stop
  logic for a server on its own port.
