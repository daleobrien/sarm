# P-256 folding reduction — derivation, bounds, and verification

Answers `prompts/04-asymmetric-crypto-algorithms.md`'s "First establish the
mathematics" section for the `p256_reduce` rewrite
(`src/crypto/p256/sqr_mul.S`), which replaced Barrett reduction (two
`p256_bn_mul` calls) with a multiplication-free Solinas-style fold.

## 1. Why a fold works here

```
p = 2^256 - 2^224 + 2^192 + 2^96 - 1
```

is a Solinas prime, which gives the exact (not modular) identity

```
2^256 = p + 2^224 - 2^192 - 2^96 + 1
```

i.e. `2^256 ≡ 2^224 - 2^192 - 2^96 + 1 (mod p)`. Any term `c·2^e` with `e ≥
256` can be rewritten, exactly mod p, as `c·2^(e-32) - c·2^(e-64) -
c·2^(e-160) + c·2^(e-256)` — each rewrite drops the max exponent present, so
repeating it terminates.

## 2. Derivation, not transcription

The repo's field representation is 4×64-bit limbs, and the exponents in the
identity above (224, 192, 96) are multiples of 32 but not of 64 — so the
fold has to operate at 32-bit granularity even though the ISA and the
field representation are 64-bit. Rather than transcribing a known table
(e.g. the one in FIPS 186-4 Appendix D, which is derived for a different,
32-bit-word-native representation and would need re-verifying against this
repo's limb layout regardless), the table used here was generated by
mechanically applying the rewrite above to each of the eight high words
`c[8..15]` of a 512-bit product `T` (`T` split into sixteen 32-bit words,
two per 64-bit limb) until every remaining exponent is in `[0, 224]`. See
`scripts/p256_reduce_derivation.py derive`.

Result (word `i` → `{output word j: coefficient}`):

```
 8 {7:+1, 6:-1, 3:-1, 0:+1}
 9 {4:-1, 1:+1, 6:-1, 3:-1, 0:+1}
10 {5:-1, 2:+1, 7:-1, 4:-1, 1:+1}
11 {3:+2, 5:-1, 2:+1, 7:-1, 0:-1}
12 {4:+2, 3:+2, 1:-1, 7:-1, 0:-1}
13 {5:+2, 7:-1, 4:+2, 6:+1, 3:+1, 0:-1, 2:-1, 1:-1}
14 {6:+3, 5:+2, 4:+1, 1:-1, 0:-1, 2:-1}
15 {7:+3, 6:+2, 5:+1, 2:-1, 1:-1, 3:-1}
```

Each entry was checked by direct exact-mod-p evaluation
(`sum_j coeff·2^(32j) ≡ 2^(32i) (mod p)`), not just trusted from the
rewrite process.

## 3. Bit widths and carry bounds — proved, not just sampled

`acc[j] = Σ coeff·c[i]`, `j = 0..7`: at most 10 terms (word 13), each
`< 2^32`, coefficients `≤ 3` in magnitude ⇒ `|acc[j]| < 10·2^32 ≈ 2^35.3` —
comfortably inside a 64-bit signed register, no overflow analysis needed
beyond that bound.

The interesting question is how many `2^256`-multiples of slop remain
after folding once — i.e. the range of `carry_final = floor(S / 2^256)`
where `S = Σ_j acc[j]·2^(32j)`. Because `S` is **exactly linear**
(homogeneous) in the sixteen input words `c[0..15]`, its extrema over the
box `c[i] ∈ [0, 2^32-1]^16` occur at box vertices — so this was checked
**exhaustively**, not sampled: `scripts/p256_reduce_derivation.py bound` computes the
closed-form min/max analytically (`R_i = Σ_j table[i][j]·2^(32j)`, then the
per-term vertex choice that minimizes/maximizes `Σ c[i]·R_i`) and
cross-checks it against direct vertex-biased evaluation of the actual
accumulate-then-propagate code path.

```
carry_final exact range: [-4, 4]
```

A second, much smaller fold (folding `carry_final` back in through the
`table[8]` pattern, since `carry_final` is exactly the coefficient of
`2^256`) leaves a residual `ext = carry_final2` bounded by interval
arithmetic to `{-1, 0, 1}` (`new_total = S_low + carry_final·R_8` with
`S_low ∈ [0, 2^256)` and `R_8 = 2^256 - p ≈ 2^224` — four multiples of
`R_8` is nowhere near a full `2^256`, so the floor can only be `-1, 0,`
or `1`). This is why **two folding passes** are required: one fold of a
512-bit input does not land inside 256 bits on its own.

## 4. Correction rounds

`ext ∈ {-1, 0, 1}` is exactly the shape the *previous* Barrett
implementation's correction rounds already handled (a small signed 5th
limb), so the new code reuses that structure unchanged: one defensive `+p`
if `ext` is negative, then two branchless conditional `-p` rounds. The
Python reference (`scripts/p256_reduce_derivation.py check`) implements this exact
sequence and asserts `ext == 0` and `0 ≤ result < p` after correction, over
2,000,000+ random 512-bit inputs plus adversarial cases (0, `2^512-1`,
`(p-1)^2`, values straddling `p` and `2^256`, many-leading/trailing-zero
limb patterns) — zero failures.

## 5. Cross-checks performed, in order

1. **Python oracle vs. derivation formula** — 2,000,000 random 512-bit
   values + edge cases, `scripts/p256_reduce_derivation.py check`: `0` failures.
2. **Hardware-faithful simulation** (explicit ASR/AND two's-complement
   semantics, matching what the assembly does register-for-register) vs.
   `pow(x, 1, p)` — 2,000,000+ cases, `scripts/p256_reduce_derivation.py check`:
   `0` failures.
3. **Differential: compiled assembly vs. Python oracle** — 3,000,000
   vectors (random + the same adversarial set) generated by the validated
   oracle, fed through the real compiled `p256_reduce` via a C driver:
   `0` failures.
4. **Permanent regression test** — `tests/unit/test_p256/reduce.c`, 292
   vectors (edge cases + random), generated by the same oracle, wired into
   `make -C tests/unit test`.
5. **Whole-suite regression** — `make -C tests/unit test` (3716 tests,
   including `p256_fe_mul`, `p256_point_mul`, ECDSA sign/verify, and full
   TLS handshake tests), `tests/test_protocols.sh`, `tests/test_files.sh`,
   `tests/test_security.sh`, and `tests/h2_browser_sim.py` (a real TLS 1.3
   + HTTP/2 page-load connection) — all pass.

## 6. Constant time

The compiled function has zero conditional branches (`loops (back edges):
0` per `regpressure.py`; grepping the function body for `b.<cond>` /
`cbz` / `cbnz` / `tbz` / `tbnz` finds none) — every decision is a `csel`
over already-computed candidates, and every memory access uses a fixed
immediate offset from `x0` (out), `x1` (T), or the `p256_p` constant
address, never a data-dependent address. This holds regardless of the
input's value, so the property does not depend on the proved carry bounds
above — it would hold even if they were wrong (the *correctness* of the
result depends on those bounds; the *timing* does not).
